Kernel totals are sums, not exclusive wall-clock accounting. Extra INT8 kernel time is ~3.07 seconds of the ~4.03-second step increase. There are only two host-to-device transfers totaling 12 bytes within each of these ranges; no weight-size transfer explains the pause.

The exact INT8 kernel name is `_int8_matmul_dequant_per_row_kernel`, defined in `backend/operations_triton.py`. Its decorator benchmarks six configurations, keyed by M,N,K. `backend/operations_mixed_precision.py` calls it through `triton_int8_linear_per_row`. Comfy-Kitchen's own Triton availability flag does not describe this independent Forge override. Disabling integrated torch.compile does not disable this autotuner.

Measured with torch.cuda.synchronize before/after each call and perf_counter. Cache size and bench_time read directly from the decorated kernel object. No server or text encoder is involved in this test.

Conclusion: the dominant pause is shape-triggered autotuning of Forge's Triton INT8 kernel. Earlier attribution specifically to native Comfy-Kitchen/cuBLASLt was incorrect; earlier ck.int8_linear tests exercised a different implementation. Smaller cold costs, including INT4, are not fully decomposed here.

To reproduce the trace table, select each NVTX_EVENTS row with text `denoiser_step=...`, then group CUPTI_ACTIVITY_KIND_KERNEL rows fully within its start/end by shortName joined to StringIds.id. Sum end-start and count rows. The instrumented ranges synchronize before ending, so completed GPU work is included.

Original observed sequence is explained by lengths 6 -> 7 -> 8 and reuse of the autotuner's in-process cache: moving the schedule boundary does not create a new shape, but a new token length does. Embeddings are computed before sampling; selection of a ready embedding changes the matrix row count (4096 image tokens plus text tokens).

## Bucket experiment

Working-tree change in backend/operations_triton.py: both INT8 GEMM autotuners now key on M_BUCKET,N,K. M_BUCKET is M for M<128, otherwise ceil(M/128)*128. Actual M, grid calculation, masks and input tensors are unchanged. Disk caching was not enabled.

Compared with a separate autotuner wrapping the same JIT function and configs but retaining the original M,N,K key. BF16 random activations, random INT8 weights and FP32 scales; runs with and without BF16 bias. Results were bitwise equal in every tested case, including cases where the two autotuners chose different configurations.

Per-row tests covered (N,K)=(6144,6144) and (6144,16384), M=4102,4103,4104,4224,4225 (the bias run for K=16384 covered 4102..4104). Scalar-scale tests with bias covered (N,K)=(256,512), M=127,128,129,130,256,257. Cache growth confirmed reuse inside a bucket and retuning at boundaries; short sizes remained separate.

Initial no-bias experiment: at M=4103, bucket call took 0.0026s versus 0.8712s for exact-key tuning (K=6144); for K=16384, 0.0079s versus 1.1329s. First use after editing JIT source also incurs compilation; one aligned shape had a ~0.45s cold cost despite no new autotuner cache entry. Bucketing does not disable JIT specialization.

Steady-state comparison used repeated triton.testing.do_bench calls, alternating order in the bias run. Square GEMM medians at M=4103: 2.506ms bucket versus 2.508ms exact. A separate down-projection control initialized the bucket with the exact autotuner's first M=4102 result to exclude independent noisy first-choice differences: M=4103 7.737ms versus 7.775ms; M=4104 7.746ms versus 7.767ms; outputs equal.

Limitation: independent first autotunes sometimes selected different configs even at the identical first shape. In one bias run, bucket down-projection was ~9ms versus ~7.8ms exact, and this slower first choice was inherited by nearby lengths. No claim of universally unchanged throughput. Full Krea generation has not been rerun with this patch; this experiment isolates the implicated kernels. New buckets/N/K still require tuning, and residual INT4 cold work remains outside this change.

Validation: both wrappers executed on CUDA, boundary/cache checks above, py_compile and git diff --check passed. No commit/push for this experiment.

## 64-row buckets and disk prewarm

User selected a maximum of 512 prompt tokens rather than characters. Both INT8
autotuners now use 64-row buckets (exact below 64), include HAS_BIAS in the key,
and enable cache_results=True. Shapes and tensors are still not padded.

Added scripts/diagnostics/warmup_krea_int8.py, which reads INT8 shape/scale metadata
from the checkpoint and benchmarks synthetic BF16 data near each bucket centre.
For batch=1 T2I with each image side between 960 and 1216 and 0..512 prompt tokens
plus 5 template positions, M=3605..6293: 43 buckets and four unique main-DiT INT8
shapes, 172 combinations. No reference images or additional template segments are
included in that bound. INT4 and attention are outside this prewarm.

Actual warmup completed 172/172 in 172.05 seconds on RTX 4060 Ti. Fresh-process
--verify-cache-only replaced the two autotuners' _bench methods with an exception
and used a different M within every bucket. All 172 calls succeeded in 1.47
seconds for the measured loop, proving disk hits rather than reuse of a previous
process's RAM cache. Full process startup took 3.82 seconds. First kernel loading
still has a startup cost; this is not a full-model timing claim.

Cache directory: C:/Users/Roman/.triton/cache. The standard Triton cache stores
all candidate timings and selects the fastest on loading. Changes to kernel
source, Triton/backend target, relevant environment or candidate configs may
invalidate entries. New shapes/buckets remain supported and tune on demand.
